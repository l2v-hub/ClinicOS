# PO12 — Piano di validazione backend dopo GO

Preparazione soltanto: nessun test applicativo, DB o server avviato da questo piano. La definizione approvata e la provenienza sono in `definition-snapshot.json`; prove future importano il codice di produzione.

1. Dominio e calcolo: tutte le 48 opzioni; massimi 16/12/28, minimo zero, soglie 18/19/23/24; venti omissioni/null distinte da zero; unknown/missing keys, -1, stringhe/frazioni/fuori dominio, note 4000/4001 codepoint, Unicode e a capo. Nessuna fascia su parziali. Enumerazioni separate 11664 equilibrio e 2304 andatura soltanto se danno copertura ulteriore senza duplicare le prove principali.
2. DB Tinetti: controllo coerente tipo/versione/answers e finalizzazione completa; SQL diretto non permette elusione dei CHECK. Una lifecycle con bozza/CAS, GET/history/current per tipo, finalizzazione/ricevuta e rettifica distinta. Test root HTTP copre gli envelope end-to-end; evitare di duplicare tutta la suite PO11.
3. Guard legacy: ramo omesso preservato; ramo identico permette altri campi; ramo diverso/array riordinato/null rispetto ad array rifiutato con 409 senza scritture; assenza/null/array vuoto distinti; JSON storico completo e incompleto immutato. Concorrenza con lock effettivo e payload stale: rilettura più recente impedisce sovrascrittura; cartella inizialmente assente serializzata tramite paziente; accesso negato o perimetro cambiato non scrive.
4. PDF: caso normale con 20 item/descrizioni e totali/fascia, più note lunghe Unicode e rettifica. Snapshot unico immutabile, archivio di tipo tinetti, retry comune. Estrarre testo e rendere/ispezionare tutte le pagine; riusare renderer/font/licenze PO11. Regressioni comuni PAINAD/Transfers già presenti scelte in base ai file condivisi effettivamente cambiati.
5. Regressioni mirate: parser/scoring PAINAD e Transfers, service CAS/replay/permessi, PDF comune se toccato, legacy scope/cartella. Root mantiene switching browser, fixture HTTP dedicata, build integrata e secret scan. Una suite mirata finale su input immutabili; ripetere solo test coinvolti dopo correzioni concrete.
6. Ricevute: typecheck backend senza build che genera client condiviso, Prisma validate se necessario, git diff check, sorgenti nuovi sotto 500 righe, font provati, runtime/manifest preservati, hash sorgenti prima/dopo prove e handoff. Ambiente PostgreSQL nativo sintetico loopback, Europe/Rome e chiusura DB registrata; nessun paziente online.

Non si dichiarano performance benchmark, CVE scan, convalida clinica o deployment dal worker. Prima di iniziare servono GO applicativo root, nuova claim implementazione e verifica baseline/contratto ancora correnti.
