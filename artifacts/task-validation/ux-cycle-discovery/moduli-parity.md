## 0. How assessment types are stored (this decides the approval path)

- `prisma/schema.prisma` → `PatientAssessment.type String`, `formVersion String`, `answers Json`, `finalSnapshot Json`. **`schema.prisma` does not need to change** to add a type.
- **But the database has hard CHECK constraints in SQL migrations** (`prisma/migrations/2026092304…_patient_assessments` → `…08_gds15`):
  - `PatientAssessment_type_check` lists every allowed `(type, formVersion)` pair.
  - `PatientAssessment_answers_check` calls a per-type plpgsql validator (`painad_answers_valid`, `tinetti_answers_valid`, `mna_answers_valid`, `gds15_answers_valid`) that pins the answer keys and score ranges.
  - `PatientAssessment_state_check` checks final snapshots per type. `gds15_snapshot_valid` even pins the **band labels** (`'Assente / Nella norma'`…) and the **`sourceSha256`** of the old source.
- Code registration is hard-coded, not data-driven: `AssessmentType` union (`backend/src/assessments/types.ts`), `CATALOG_FORMS` (`catalog.ts`), `input.ts`, `service.ts`, `history.ts`, `current.ts`, `access.ts`, `pdf-renderer.ts`, `pdf-service.ts`, `tools/capabilities/assessments.ts`. The frontend has `CATALOG_TYPES` / `CLINICAL_MODULES` (`lib/assessments/assessmentCatalog.ts`), and `parseAssessmentCatalog` **rejects anything that is not exactly 5 items**. It also has `ASSESSMENT_VERSIONS`, per-type definition, validation and draft-store files, and the Form/Summary components.
- Finalized snapshots are immutable, and the snapshot carries the item labels. Changing wording/options/scoring of an existing scale therefore means a **new `formVersion`**. Old finals stay valid under the old version.
- **Conclusion:** (a) any new type (Barthel, UCLA) and (b) any change to wording, options or scoring that is persisted in a snapshot (GDS, MNA, Tinetti) both require a **new SQL migration** (a new CHECK pair + validator). There is no `schema.prisma` model change, but it is a DB migration that needs owner approval. Pure layout changes to the on-screen form and the generated PDF are frontend/renderer only. The renderer is backend code (`pdf-renderer.ts`) but needs no migration. Bump the renderer version string.

### Cross-cutting layout gap (applies to all 5 forms)

To make a paper-identical PDF you would rewrite the renderer per form into a table layout: a header band, all options printed with the selected one ticked, a bands box and a signature line. That is roughly one table-drawing helper plus one layout per form in pdf-lib. On screen, a "paper" view can reuse the same table structure.

## Open questions (genuine)

3. **GDS / Tinetti / MNA wording switch** affects only new assessments; old finalized records keep the old wording (immutable snapshots). Is that acceptable? Do you also approve the DB migrations (new formVersions; no `schema.prisma` model change)?
4. **UCLA**: the PDF is an informational sheet. What do staff actually fill in? (a) NPI sleep domain only (frequency × severity)? If so, is "0 = absent" valid even though the text says "da 1 a 12"? Is the NPI caregiver-distress score included? (b) CSWS/ASWS is paediatric and has no item list. Is it really wanted for a geriatric facility? 5. **AI disclaimer footers** on GDS/MNA ("This is for informational purposes only… AI responses may include mistakes.") and UCLA (Italian equivalent): reproduce them verbatim or omit them?
6. **Source typos**: keep "imbottigliato/imboccato" (Barthel), "OBSERVAZIONALE" and "consolatore" (PAINAD) verbatim for "identical", or correct them as the app does today?
7. **Signature line**: the paper Barthel and Tinetti have "Firma dell'Operatore / Valutatore". Should the generated PDF print a blank signature line, or print the authenticated author name in its place?
8. **App-only extras** (notes field, provenance/bibliography, codice fiscale, camera/letto, timestamps in the PDF): keep them (e.g. in a footer block or a second page) or drop them for strict paper identity?
