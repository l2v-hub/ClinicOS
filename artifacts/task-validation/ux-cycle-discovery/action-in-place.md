# "Act on it where you see it" — discovery report

Date: 2026-10-03 · Mode: READ-ONLY discovery (no source edits) · Branch: fix/389-facility-resident-scope

Owner principle: when you see an item and your profile can act on it, the action must be **right there**.
In patient therapy, tapping a drug must let a nurse **administer** it without hunting for another screen.

Evidence: local stack (backend 3103 / vite 5203 / DB `disc_act`, demo seeds), Playwright probes per role.
Screenshots and logs are in `action-in-place/` next to this file:

- `Infermiere_1-02-therapy-attivi.png`, `-03-after-row-click.png`: tapping a row does nothing.
- `Infermiere_1-04-calendar-slot.png`: the only place in the chart where Somministra appears.
- `Infermiere_1-06-adesso-apri-lands.png`: a late dose's «Apri» opens Farmaci attivi, with 0 Somministra buttons.
- `Medico_1-*`: read-only slot detail. `OSS_1-*`: no Terapia section.

**Shortest path today for a nurse who is reading the drug list and wants to administer Ramipril 08:00:**
Calendario sub-tab, then scroll or find the 08:00 hour, then tap the hour, then find the drug inside the panel, then Somministra.
That is **3 extra taps plus a visual search**, and the nurse loses the row they were reading.
Coming from Turno › Adesso it takes one more tap: «Apri» lands on Farmaci attivi.

Backend for administering already exists and needs no change for scheduled doses:

- `POST /therapy-slots/confirm`, capability `administration.confirm`
- `POST /therapy-slots/not-administered`, capability `administration.record_not_administered`
- Both go through `therapies/administration-record.ts` (Serializable transaction, actor taken from the session).
- Frontend client: `lib/therapyAdministrationWrite.ts#recordAdministration(info, outcome)`.
- Body: `{patientId, therapyId, date, fascia, ora}`. Drug, dose and route are resolved on the server.
- Read model: `GET /therapy-slots?date=` → `patientGiroTime(slots, patientId, time)` (used by PatientTherapySlotDetail).

Role baseline (`backend/src/authz/baseline.ts`):

Verified on the local stack with simulator tokens:

- Nurse `PUT /patients/x/therapies/y` → **403 capability_denied therapy.update**.
- Nurse `DELETE /patients/x/therapies/y` → **403 therapy.delete**.

So the nurse is **shown prescriber actions she cannot use**, and is **not shown the one action she can use**.

## 3. Interaction spec — "tap a drug in patient therapy"

### 3.1 Shared building block (no new rules)

Create one `DrugDosePanel` that wraps the existing pieces:

- **Data:** `GET /therapy-slots?date=<today>` (cached through `cachedGetJson`, as `PatientTherapySlotDetail` does today). Filter `patients[patientId].administrations` by `therapyId`, across all fasce of the day.
- **Rows:** reuse `TherapyGiroRows` (or its row renderer), so the buttons, the reasons (`MOTIVI`), the «altro» note, the in-flight lock, focus handling and the status badges are **identical to the Giro**.
- **Writes:** `recordAdministration(info, outcome)` from `lib/therapyAdministrationWrite.ts`. It then calls `invalidateCachedGet('/therapy-slots')` and refetches. The success/error message is the same text as in `PatientTherapySlotDetail` (`role=status` / `role=alert`).
- **Gating:** use exactly the current rule, `canAdminister = useCan('administration.confirm') && useCan('administration.record_not_administered') && role !== 'admin'`.
- **Confirmation:** if `/auth/me` marks `administration.confirm.requiresConfirmation` (supervisor), Somministra opens the existing `ConfirmDialog` («Confirm administering {farmaco} {dose} to {paziente} at {ora}?») before posting. The «Non somm.» flow already has a confirm step (choose a reason, then «Conferma»), so keep it.
- Never auto-administer, never skip the reason, never accept a client-side dose/time (the server resolves them). A 409 (already given / changed) shows the server message and refetches.

### 3.3 Outside the chart (same panel, same rules)

- **Turno › Adesso** (`terapia-ritardo` / `terapia-imminente`): inline Non somm. / Somministra on the row. «Apri» moves to a secondary link and lands on **Farmaci attivi with that drug expanded** (`focusTherapyId` already exists in `PatientDetail.tsx:2513`).
- **Diary «Terapia aggiunta … apri»** (`DiarioPazienteTab.tsx:596`): lands with the drug expanded (same focus mechanism).

### 3.4 Acceptance checks for the fix (to put in the task contract)

1. Nurse: Farmaci attivi → tap Ramipril → Somministra visible within 1 tap → POST `/therapy-slots/confirm` 200 → badge «HH:MM · operator». Giro, Calendario and Adesso show the same state after refetch.
2. Nurse: «Non somm.» requires a reason. «Altro» requires the note. Then 200, and the reason appears in Storico.
3. Doctor: the same tap gives a read-only panel with no Somministra. Modifica/Sospendi are present.
4. Nurse: no Modifica/Sospendi/Elimina/Riattiva/«+ Aggiungi» anywhere in Terapia (no 403 reachable from the UI).
5. Supervisor: Somministra opens a ConfirmDialog before the POST.
6. OSS: no Terapia section (unchanged). Admin: read-only.
7. Adesso late dose: administer from the queue row. The row disappears or updates on refresh.
8. A double tap or a concurrent giro tap gives a single record (in-flight lock, plus server 409 «Terapia già erogata» shown verbatim).

## 4. Requires owner decision (do not implement silently)

- **F4 PRN administration:** new endpoint and probably a schema change. Today's unique key `(therapyId, date, fascia)` allows 1 dose per fascia per day.
- **F8 per-reader «presa visione»** on diary entries: new model.
- **F16 scale-due rules:** a clinical rule (intervals per scale) for the health direction.
- **F6:** should `requiresConfirmation` also be enforced server-side (e.g. a confirm token)? Today it's advisory only.
